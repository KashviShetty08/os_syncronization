# Operating System Synchronization Assignment

## Overview

This project demonstrates two classical synchronization problems in Operating Systems:

1. Readers–Writers Problem
2. Dining Philosophers Problem

Both problems are implemented using two synchronization techniques: semaphores and monitors. The programs use Python threads to demonstrate how multiple processes or threads access shared resources while maintaining synchronization.

The project also generates HTML-based visualizations that display the execution events, thread states, and event logs.

## 1. Readers–Writers Problem Using Semaphores

### Description

The Readers–Writers problem involves multiple readers and writers accessing a shared variable. Multiple readers can access the shared data simultaneously, but a writer must have exclusive access while modifying it.

The implementation uses two semaphores:

- `mutex`: Protects the reader count.
- `resource`: Controls access to the shared data.

The first reader acquires the resource semaphore, preventing writers from entering. The last reader releases it. Writers acquire the resource semaphore before modifying the shared variable.

### Synchronization

- Allows multiple readers to read simultaneously.
- Ensures writers access the shared resource exclusively.
- Uses reader preference, so continuous reader activity may cause writer starvation.

## 2. Readers–Writers Problem Using Monitors

### Description

This implementation uses Python's `threading.Condition()` to coordinate readers and writers.

The monitor maintains the reader count, the active-writer state, and the number of waiting writers. Readers wait while a writer is active or waiting. Writers wait until there are no active readers or writers.

### Synchronization

- Allows concurrent reading.
- Prevents readers and writers from accessing the shared resource simultaneously.
- Gives waiting writers preference over new readers.
- Reduces the risk of writer starvation, although starvation freedom is not guaranteed.

## 3. Dining Philosophers Problem Using Semaphores

### Description

The Dining Philosophers problem represents multiple philosophers sitting around a table, sharing chopsticks. Each philosopher alternates between thinking and eating. A philosopher must acquire both adjacent chopsticks before eating.

The implementation uses:

- One binary semaphore for each chopstick.
- A `room` semaphore initialized to `N - 1`, where `N = 4`.
- Four philosopher threads, each performing two rounds of thinking and eating.

The room semaphore allows at most three philosophers to attempt to acquire chopsticks at the same time. This prevents the classic circular-wait deadlock under normal execution.

### Synchronization

- Ensures each chopstick is acquired by only one philosopher at a time.
- Requires both adjacent chopsticks before eating.
- Prevents the classic deadlock using the room semaphore.
- Does not guarantee that every philosopher will eventually eat.

### HTML Visualization

The generated `dining_semaphore.html` page displays philosopher states, execution messages, and an event log. It includes Play, Pause, Next Event, and Reset controls.

## 4. Dining Philosophers Problem Using Monitors

### Description

This implementation uses `threading.Condition()` to synchronize the four philosopher threads.

Each philosopher has one of three states:

- `Thinking`
- `Hungry`
- `Eating`

A philosopher can start eating only when both neighbouring philosophers are not eating. When a philosopher finishes, the monitor changes their state to `Thinking` and notifies waiting threads.

### Synchronization

- Prevents neighbouring philosophers from eating simultaneously.
- Checks the philosopher's state before allowing them to eat.
- Uses condition-variable waiting and notification to coordinate access.
- Prevents deadlock under normal execution, but does not guarantee starvation freedom.

### HTML Visualization

The generated `dining_monitor.html` page displays philosopher states, execution messages, and an event log. The visualization provides Play, Pause, Next Event, and Reset controls.

## Deadlock and Starvation

**Deadlock** occurs when threads wait indefinitely for resources held by one another.

**Starvation** occurs when a thread is repeatedly denied access to a resource while other threads continue to make progress.

The semaphore-based Dining Philosophers implementation uses a room limit of `N - 1` to prevent the classic circular-wait deadlock. The monitor-based implementation permits a philosopher to eat only when neither neighbour is eating.

The Readers–Writers semaphore implementation uses reader preference, which may starve writers under continuous reader activity. The monitor implementation gives waiting writers preference, but does not guarantee that readers or writers will never starve. Neither Dining Philosophers implementation guarantees starvation freedom.

## Conclusion

This project demonstrates how semaphores and monitors can coordinate concurrent threads and protect shared resources. The Readers–Writers implementations illustrate how different synchronization policies affect access to shared data, while the Dining Philosophers implementations demonstrate strategies for preventing deadlock.

The HTML visualizations provide a practical way to observe thread-state changes and execution events, making the synchronization concepts easier to understand.
